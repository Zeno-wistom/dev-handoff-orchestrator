# 开发协同与会话管理

## 一轮开发

1. 从已有项目资料确定当前目标、待实现功能、已批准的产品约束和验收标准；证据不足就标明未知。
2. 接收用户从 ChatGPT 发来的 Prompt 后，核对已批准范围。普通实现由 Codex 决定；显著影响费用、开发时间或用户体验的取舍，先解释方案与推荐，等用户批准。
3. 完成必要的编码、检查与测试，明确区分：已实现且验证、已实现但未验证、仍待处理。对本地完成状态只使用代码与测试证据，不把顾问分析当成执行记录。
4. 按 `templates.md` 输出简短汇报，方便用户交给 ChatGPT 解读。能直接继续的工作不用反复制作长报告。
5. 当用户确认新方向时，以新确认的决定为准；历史被否决方案不可重新当作需求。

## 决策与信息边界

- 用户负责产品目标、关键交互和重大取舍，Codex 负责技术实现，ChatGPT 担任分析顾问；不能把任何一方的建议误当作另一方已经批准。
- 报告中的技术内容可以保留文件、命令、复现步骤和测试结果，同时附上简短的大白话解释。
- 只传与当前任务有关的摘要和必要证据，不包含密钥、令牌、密码、无关个人数据及不必要的私有源码。
- 原项目的任务清单和已批准决策仍是依据；项目记忆或历史聊天可辅助理解，但交接时应明确当前状态。

## 进度更新

- 根据现有阶段计划、子任务验收条件和真实证据计算双层进度；若缺少总阶段数或已验收证据，用「未知」代替猜测。
- 阶段定义变化时说明原因。阶段推进或出现主要阻塞时更新；微小操作无需反复刷进度。
- 不把「当前功能做完」包装成「整个产品已完成」，也不要求为未知的未来版本编造路线图。

## 会话健康判断

目标是保持对当前任务的准确理解，同时尽量节省交接与检查成本；不将聊天轮数、累计文本量或主观流畅感当成上下文剩余容量。

### 检查触发

1. **明确任务边界**：一个可验收模块结束，即将进入相对独立的新模块 → 直接建议开启新会话，并附四项精简交接；已经决定切换时，不再检测旧会话。
2. **同一功能连续讨论**：在每次阶段性结果汇报时，或多轮实质讨论后最近一次自然答复中，轻量核对本轮建议是否符合已批准约束。把这视为工作质量复核，不中断对话，也不按固定轮数宣布“满了”。
3. **出现异常**：用户指出遗漏、方案违反已批准决定、先前已否决的要求被重新执行 → 立即查看可获得的原始决定及最近行为，先纠正；下轮再次实际运用该约束时复核是否仍出错。
4. **证据不足**：找不到可靠原始决定、无法读取上下文数据或没有办法独立核对时，记录缺口，不宣布健康或耗尽。

### 判断动作

- **继续**：当前阶段连贯、可见建议与已确认约束没有已发现冲突。无须每轮报告健康状态。
- **纠正并复查**：出现首次可核实的混淆，先给出正确决定并改正下一步方案；必要时要求最小相关证据。
- **建议开启新会话**：独立新阶段开始，或纠正后仍可复现违反关键约束、并已排除需求含糊／信息冲突。说明具体证据，并附精简交接。不能断言“上下文已满”。
- **仅 Codex 可考虑压缩**：依据实际可读取的上下文用量、压缩事件和当前可用工具；无数据则标未知。不要把账号限额当作对话上下文；只按已支持的能力操作。

ChatGPT 端的检查只能在其响应时执行，不存在后台常驻自测；回答能复述旧要求，并不保证接下来的设计一定遵守，需要对照实际建议。两端会话独立管理，切换动作留给用户。

### 交接尺度

- **日常反馈**：简短成果、测试证据、风险、下一步和有数据依据的双层进度。
- **新会话**：默认四项：目标、当前结果／未验证事项、已批准／否决的关键决定、下一步及验收标准。只附恢复当前任务必需的文件、分支或错误。
- **复杂恢复**：多项相互依赖的约束、长期复杂阻塞、关键决策冲突或用户明确要求时，改用六项详细交接。
- 只为能继续工作传递必要上下文，避免为了形式完整复制全量历史。具体模板见 `templates.md`。

## 新会话接续

- 先恢复当前目标、已完成的证据、关键批准和未批准范围以及下一步，尽量只读取恢复本轮工作必需的文件。
- Codex 核对交接涉及的分支、文件和测试结果是否仍匹配当前工作区；ChatGPT 如无本地证据，明确其无法验证。
- 遇到事实冲突或关键材料缺失时指出具体差异，暂停依赖争议决定的工作；不要机械重问已经批准的事项。
- 用一段清晰的话告诉用户已恢复的目标、当前进度和接下来要做什么。新会话只核验交接是否可用，不做旧会话容量测试。
