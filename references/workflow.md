# 开发协同与会话管理

## 一轮开发

1. 从已有项目资料确定当前目标、待实现功能、已批准的产品约束和验收标准；证据不足就标明未知。
2. 接收用户从 ChatGPT 发来的 Prompt 后，核对已批准范围。普通实现由 Codex 决定；显著影响费用、开发时间或用户体验的取舍，先解释方案与推荐，等用户批准。
3. 完成必要的编码、检查与测试，明确区分：已实现且验证、已实现但未验证、仍待处理。对本地完成状态只使用代码与测试证据，不把顾问分析当成执行记录。
4. 按 `templates.md` 输出简短汇报，方便用户交给 ChatGPT 解读。能直接继续的工作不用反复制作长报告。
5. 当用户确认新方向时，以新确认的决定为准；历史被否决方案不可重新当作需求。

## 决策与信息边界

- 用户负责产品目标、关键交互和重大取舍，Codex 负责技术实现，ChatGPT 担任分析顾问；不能把任何一方的建议误当作另一方已经批准。
- 报告中的技术内容可以保留文件、命令、复现步骤和测试结果，同时附上简短的大白话解释。
- 只传与当前任务有关的摘要和必要证据，不包含密钥、令牌、密码、无关个人数据及不必要的私有源码。
- 原项目的任务清单和已批准决策仍是依据；项目记忆或历史聊天可辅助理解，但交接时应明确当前状态。

## 进度更新

- 根据现有阶段计划、子任务验收条件和真实证据计算双层进度；若缺少总阶段数或已验收证据，用「未知」代替猜测。
- 阶段定义变化时说明原因。阶段推进或出现主要阻塞时更新；微小操作无需反复刷进度。
- 不把「当前功能做完」包装成「整个产品已完成」，也不要求为未知的未来版本编造路线图。

## 会话管理

- **Codex**：仅使用当前实际可见的上下文用量或压缩事件作为直接证据；用量不可得时报告未知。结合任务自然边界、持续遗失已批准约束等迹象建议继续、压缩或换会话；是否有压缩操作以当前环境支持为准。
- **ChatGPT**：不能据此假定它能读出准确的剩余上下文。必要时用已有真实决策做小型理解校验；单次答错先纠正并复查，不把错误直接归因于上下文耗尽。
- 两端会话各自按需更换，不要求数量一致；建议切换时说明原因，但由用户操作。
- 需要换会话、跨阶段或复杂恢复时，按 `templates.md` 的六项结构生成一次复制的完整交接 Prompt。

## 新会话接续

- 先恢复当前目标、已完成的证据、关键批准和未批准范围以及下一步，尽量只读取恢复本轮工作必需的文件。
- Codex 核对交接涉及的分支、文件和测试结果是否仍匹配当前工作区；ChatGPT 如无本地证据，明确其无法验证。
- 遇到事实冲突或关键材料缺失时指出具体差异，暂停依赖争议决定的工作；不要机械重问已经批准的事项。
- 用一段清晰的话告诉用户已恢复的目标、当前进度和接下来要做什么。
