# 交接与汇报模板

按实际内容填值；没有的项目写“无”“未知”或“未验证”，不为填模板虚构事实。

## 日常短报告（默认）

一次普通功能完成或日常向顾问汇报时，先用短格式，避免每次输出项目全历史、完整六项交接或长路径；用户有疑问再附具体文件/日志。尚未有测试证据就标“未验证”，不能写“已完成”。

```text
大白话结论：这一轮实际改变了什么。
项目总进度：[八格或????????] 已验收/总阶段，或未知（有明确阶段时）
当前阶段：[八格或????????] 已完成/总子任务，或未知（有明确阶段时）
本轮完成：...
实际测试：...（未执行则说明）
待决策/风险：...（没有则写无）
当前步骤：...
下一步：...
进度依据：...（已有任务/测试证据，无法核实时标未知）
```

**何时升级为完整交接**：准备开启新会话、跨重要阶段、遭遇复杂阻塞、需要恢复遗漏的重大已批约束，或用户明确要求完整上下文。此时使用下文“一次复制六项交接 Prompt”；普通短报告不会因此被判为交接失败。

## 双层进度与交付

复用已有阶段/验收清单，不另建常驻台账。没有计划但任务范围已清楚时，在本轮列出最少阶段及完成条件即可。尚不清楚总项目范围时只能报告当前阶段的已知进度。

- 总进度以**已验收阶段数**为单位；当前阶段以**满足完成条件的子任务数**为单位。不要混合文件数、测试数与功能数作为一个分母。
- 按 `floor(8*d/t)` 填充八格；`0 <= d <= t` 且 `t > 0` 才可计算。完成为 `[████████]`，未开始为 `[░░░░░░░░]`。数量已知但工作量不等时说明这是计数进度。
- 缺少任一可靠计数，使用 `[????????] 未知（缺少什么证据）`；不要用八个空格暗示 0%。阶段还没有开始可以标“待开始”；无阶段的一次性小任务不强行分层。
- 修改范围/阶段总数时说明新增/拆分及原因；不能通过缩小分母掩盖未完成工作。`已写入，未测试`、`顾问建议完成`、`等待审批`不计为已验收。
- 每次更新包含证据来源，例如 `tasks.md 阶段2验收项；本轮 npm test 12/12；浏览器主流程通过`。只能写实际执行的检查。

```text
大白话摘要：用户现在能做什么，尚有哪些限制。
项目总进度：[进度条或????????] 已完成/总阶段或未知
当前阶段：[进度条或????????] 已完成/总子任务或未知（阶段名称）
本轮完成：具体结果及完成条件
当前步骤：正在处理或阻塞的事项
下一步：最小可执行动作
进度依据：现有任务记录/本轮清单 + 实际验收证据

关键修改及文件：可点击的文件位置和用户可见影响
测试结果：执行命令或实际操作、结果、必要证据
未验证事项：未执行的检查、原因和剩余风险
问题或风险：事实及影响，无则写无
需要用户决定：推荐、显著取舍、等待中的动作；无则写无
建议的下一步：具体动作；任务已完成且用户要求停止时写等待反馈
```

## 显著取舍审批

```text
需要你决定：一个清楚的问题
方案 A：对用户体验、交付时间、费用的具体影响（不确定时说明）
方案 B：同上
我的推荐：方案及原因
已获批范围：可以继续的独立工作
等待批准：将暂停的具体变更
```

通过当前环境支持的用户问答机制请求决定，不把关键决策藏进普通进度。可准备可审核的方案，但不能先实施关键变更再补批。普通实现无需套用这个模板。

## Codex → ChatGPT 完整交接 Prompt（按需，用于换会话或复杂恢复）

**只在完整交接触发时**把以下全部六项合在同一个独立代码块输出，便于一次复制；不得拆成六个代码块。必要的双层进度和证据合并到对应项，不复制完整历史或密钥。

```text
你是本项目顾问，协助解释、分析与下一轮任务交接。代码实现状态仅以 Codex 本地执行证据为准；建议不能替代用户审批。

1. 当前目标
本轮目标、适用项目标识与必要的环境/代码版本定位。
项目总进度：[八格或????????] 已完成/总阶段或未知
当前阶段：[八格或????????] 已完成/总子任务或未知（名称）
当前步骤：……；进度依据：……

2. 已完成的工作
本轮完成：具体成果、关键文件和实际验证；区分已实现、已验证、未验证。

3. 关键已批准决定
用户明确批准的方向/约束及出处；没有证据就标为待确认，不把你的建议列入批准。

4. 当前问题及必要证据
错误、最小日志、复现条件、风险、上下文用量（未知则直说）；只包含本轮所需证据。

5. 下一步任务
下一步：明确动作、验收标准；请解释成果和取舍，并形成用户批准后能交给 Codex 的执行 Prompt。

6. 明确禁止或尚未获批的改动
禁止范围、待批决策、自动咨询/绑定边界。不得通过新会话重置审批边界。
```

Codex 接收时按 workflow“新会话接收”核验当前工作区后执行。ChatGPT 接收时先解释现状，有显著取舍先给推荐并等待用户决定。

## 技术咨询包

“已批准约束”只列用户实际批准且有出处的内容，无则写“无已提供证据”。Skill 默认操作边界或 Codex 的建议另标“操作边界/建议”，不得写成用户已批准的产品要求，也不得从其他场景继承决定。

```text
用途：普通技术咨询，非产品审批或执行记录
请求标识：本轮唯一标识
当前目标：……
已批准约束：……
具体问题：……
最小去敏证据：……
期望回复：推荐方案、依据/官方来源、主要取舍、需要本地验证什么。
请将未经验证的推测明确标出；不要声称已经修改或测试本地项目。
```

## ChatGPT → Codex 可执行 Prompt

```text
使用 $dev-handoff-orchestrator 继续当前项目。
目标与验收标准：……
用户已批准：……（批准出处；未获批的选项不得进入实现要求）
参考材料：……（顾问意见作为建议，技术事实需必要核验）
修改范围：……
明确禁止/尚未批准：……
执行：完成实现、必要测试和修复；从本地证据报告双层进度，列出关键文件、测试、未验证事项、风险及下一步。
咨询模式与绑定：沿用用户明确指定且本轮可核验的绑定；无可用浏览器或缺少绑定时生成手动交接 Prompt，不猜测目标会话。
```
